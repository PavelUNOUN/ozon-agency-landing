# Чат сайта и Telegram: архитектура следующего этапа

Сейчас сайт отвечает по публичному файлу `knowledge/public-faq.json`. Это справочник с заранее утверждёнными ответами, без модели, API и сохранения переписки. Сайт читает его через `assets/chat.js`. Для работы нужен обычный веб-сервер, который отдаёт JSON с типом `application/json`.

## Единый источник знаний

- Хранить только утверждённые материалы с полями `id`, `title`, `body`, `source`, `updated_at`, `visibility`, `owner`.
- Разделять `public` (можно цитировать посетителям) и `internal` (нельзя выдавать публичному чату). Публичные ответы сайта и Telegram строить только из `public`.
- Изменения принимать через редакторский процесс: автор → проверка фактов и условий услуги → публикация версии. Нельзя автоматически обучать базу на сообщениях пользователей.
- Хранить историю версий, чтобы можно было восстановить источник каждого ответа.

## Серверный контур

Один HTTPS API обслуживает сайт и Telegram-бот. Оба клиента передают вопрос и канал, получают одинаковый формат ответа. Ключи модели и база знаний остаются на сервере.

1. Проверить размер запроса, частоту обращений и допустимый формат. Удалить управляющие инструкции из маршрутизации, не выполнять ссылки или код из вопроса.
2. Найти релевантные записи только среди опубликованных публичных материалов. Если данных нет, вернуть безопасный отказ и контакт человека.
3. Генератор составляет черновик ответа только по найденным записям и возвращает ссылки на их `id`. Контекст из вопроса и найденных документов рассматривается как данные, не как команды.
4. Отдельный проверяющий контур сверяет каждое утверждение с записями, запрещает неподтверждённые обещания, внутренние данные и инструкции по обходу правил. При сомнении возвращает отказ или передаёт разговор человеку. Проверка моделью дополняет, но не заменяет серверные правила доступа.
5. Логировать версию базы, id использованных записей, итоговый статус и обезличенные технические метрики. Срок хранения и согласие на персональные данные определить до запуска.

Пример контракта: `POST /api/chat` с `{ "message": "...", "channel": "web", "session_id": "..." }`; ответ `{ "answer": "...", "source_ids": ["price"], "status": "answered|unknown|rejected|handoff" }`. Клиент никогда не получает API-ключ модели, системные инструкции или внутреннюю базу.

## Проверки перед подключением модели

- Запросы с попыткой получить системные инструкции, ключи, внутренние документы, персональные данные или заставить модель игнорировать правила → `rejected`.
- Запросы о цене, составе работ и сроках без подтверждения в текущей версии знаний → `unknown` или `handoff`.
- Проверки на выдуманные источники, смену условий услуги и ответы вне темы.
- Сквозной тест одного вопроса через сайт и Telegram: одинаковые факты и версия базы.
- Нагрузочное ограничение и журнал ошибок без записи секретов.

До появления сервера чат остаётся справочником. Не следует показывать его как AI-консультанта или обещать, что он проверяет произвольные ответы второй моделью.
